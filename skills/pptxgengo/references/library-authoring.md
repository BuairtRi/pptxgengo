# Library discovery and bindings

Search the installed SQLite index through the CLI; retain source definitions,
asset hashes and project pins as the durable inputs.

```sh
pptxgengo design library-find --query 'phase roadmap' --kinds template --summary
pptxgengo design library-inspect --id lifecycle/three-phases --summary
pptxgengo design library-authoring --template lifecycle/three-phases
pptxgengo design library-preview --id lifecycle/three-phases
```

Inspect purpose, slots, item counts, content groups, previews and dependencies
before choosing a template. Use exact keys; supply all required content and
retain stable item identities. Match scenario and content structure separately.
Read a fitting report as measured capacity evidence, not visual approval.

Use `project scaffold --stock` for readable shared-template YAML. Keep template
geometry in its definition and copy in named content/bindings. Use source-managed
claims/evidence and visible illustrative labels; examples are not client facts.
A library match cannot invent evidence or decide a real operator approval.

Use the packaged template browsing PPTX for visual selection or copying into a
native PowerPoint working deck. Its media are illustrative placeholders. Actual
asset embedding requires verified available originals or project registrations.
A reusable content slide requires an operator-supplied approved revision; no
curated content inventory is bundled.

The older `pptxlib` semantic-contract route remains repository-only; when that
specific route is required, read `docs/legacy-authoring/library-authoring.md`.
Keep its exact contract/qualification limits separate from V11 templates.
