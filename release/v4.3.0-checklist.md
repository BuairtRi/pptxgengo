# v4.3.0 private release execution checklist

This is a candidate checklist. It does not establish a published release or authorize
moving an existing tag. Follow [the maintained release runbook](CI.md).

## Pre-tag gates and scope

The reviewed commit must be merged to `main`, pass its applicable GitLab checks,
and retain the complete semantic source audit and named macOS qualifications.
Windows PowerPoint/runtime qualification remains deferred. The tag must identify
the same commit verified on both configured `origin` push destinations.

Current YAML defaults are:

```text
PPTXGENGO_PACKAGE_KIND=cli-only
PPTXGENGO_BROWSING_POLICY=templates-only
PPTXGENGO_OFFLINE_MODEL=true
release/default-bundle.txt=v11
```

The template-only resource job regenerates the browsing deck and SQLite from the
tagged source/compiler, includes fonts, catalog, registered diagram SVG originals,
the complete presentation skill and its reference files, `install-skill.py`, and
`SKILL-INSTALL.md`. The signed closed inventory records actual bytes. Reusable
slides and private photo/branding originals are deferred; no private input URL is
needed for this scope. The optional offline model remains a separate signed-manifest
attachment, outside the six executable archives.

The two exhaustive quantitative/commercial catalog tests run in the dedicated
nightly/on-demand `composition-catalog` job without `-short`. Representative units
remain in the main/tag short suite. Full local audit evidence is required before
tagging; the release resource job independently renders the whole template library.
No race jobs or unavailable Windows desktop jobs are added to tags.

Read-only GitLab review on 2026-10-09 confirmed project 17 and its package registry
are private, protected `v*` tags require Maintainers, and existing Apple/Azure/privacy
variable keys are protected. The active schedule runs at 01:00 America/Los_Angeles.
The source pipeline has four ordinary main jobs and 28 protected release jobs in
GitLab dry-run lint; both lint results are valid with no errors/warnings. That
simulation used the existing protected `v4.2.1` ref, not a new v4.3.0 tag.

The release compiler is pinned to Go 1.27.2 with official archive checksums.
The pre-tag scan of the previous Go 1.27.1 compiler failed on reachable standard
library vulnerabilities; the patch compiler must pass all three platform source
scans before tagging. The module minimum remains Go 1.27.1 for source compatibility;
it does not weaken the exact release compiler/binary gate.

## Cut the tag only after final gates pass

Run in the clean integrated repository, using the exact reviewed main object ID:

```sh
release_commit=REVIEWED_MAIN_OBJECT_ID
# Compare these results with release_commit and confirm the working tree is clean.
git status --short
git rev-parse main
git ls-remote https://github.com/BuairtRi/pptxgengo.git refs/heads/main
git ls-remote git@gitlab.samcott.com:riscott/pptxgengo.git refs/heads/main
# Confirm v4.3.0 is absent locally and on both destinations before creating it.
git tag --list v4.3.0
git ls-remote https://github.com/BuairtRi/pptxgengo.git 'refs/tags/v4.3.0*'
git ls-remote git@gitlab.samcott.com:riscott/pptxgengo.git 'refs/tags/v4.3.0*'

git tag -a v4.3.0 "$release_commit" -m 'Release v4.3.0'
git push origin refs/tags/v4.3.0

git ls-remote https://github.com/BuairtRi/pptxgengo.git 'refs/tags/v4.3.0*'
git ls-remote git@gitlab.samcott.com:riscott/pptxgengo.git 'refs/tags/v4.3.0*'
```

Compare both tag object IDs and peeled commit IDs. Every write uses the configured
`origin` dual push, with no separately named GitLab push. A partial push is diagnosed
and the same immutable tag may be forwarded; never recreate it with a different
object. Monitor the private tag pipeline and all required jobs:

```sh
glab api --hostname gitlab.samcott.com 'projects/17/pipelines?ref=v4.3.0&per_page=5'
# Substitute the returned exact pipeline ID.
glab api --hostname gitlab.samcott.com 'projects/17/pipelines/PIPELINE_ID/jobs?per_page=100'
```

Publication is automatic after resource/build/sign/scan/platform-verification and
manifest-attestation gates. A signed archive alone is not the release gate.
Privacy, signature and uploaded-byte round-trip checks precede GitLab Release
creation. Do not publish manually to bypass a failed gate.

## Independent download verification

Use a trusted source checkout of the released commit. Download to a new private
directory; authenticate with the existing GitLab CLI login and do not echo tokens.
This command downloads exact asset bytes rather than formatting JSON responses:

```sh
downloads=/absolute/new/private/v4.3.0-downloads
mkdir -m 700 "$downloads"
glab release download v4.3.0 \
  --repo https://gitlab.samcott.com/riscott/pptxgengo --dir "$downloads"
```

On trusted Linux x86_64 (for example an owned home-lab qualification job/pod),
initialize the pinned Sigstore trust and verify the exact project/tag identity,
issuer, Rekor inclusion and signed timestamp **before extraction or execution**:

```sh
tools_dir=/absolute/new/private/v4.3.0-tools
trust_dir=/absolute/new/private/v4.3.0-trust
bash scripts/release/install-tools.sh --bin-dir "$tools_dir" --only cosign
export PATH="$tools_dir:$PATH"
bash scripts/release/sigstore.sh initialize --home "$trust_dir"
bash scripts/release/sigstore.sh verify --home "$trust_dir" \
  --blob "$downloads/manifest.json" --bundle "$downloads/manifest.sigstore.json" \
  --version v4.3.0
```

The pinned installer supports Linux x86_64; do not run it on a Mac. Verification
uses the trusted checkout's `release/sigstore-policy.json`, not one supplied by an
unverified archive. After signature verification, enforce the expected source
commit, package scope, six targets and every signed file hash:

```sh
# release_commit is the previously reviewed, mirrored main object ID.
go run ./scripts/cmd/release-ci verify "$downloads" v4.3.0 "$release_commit"
jq -e --arg commit "$release_commit" '
  .version == "v4.3.0" and .commit == $commit and
  .package_kind == "cli-only" and .browsing_policy == "templates-only" and
  .windows_runtime_qualified == false
' "$downloads/manifest.json"
```

For each target, extract with the trusted bounded extractor into a new directory,
then verify executable target/version/source markers, Go build identity and the
signed executable hashes against the downloaded evidence:

```sh
target=darwin-arm64
extracted=/absolute/new/private/v4.3.0-darwin-arm64
archive="$downloads/pptxgengo-v4.3.0-$target.tar.gz"
go run ./scripts/cmd/release-ci extract "$archive" "$extracted"
go run ./scripts/cmd/release-ci verify-binaries "$extracted" "$target" v4.3.0 "$release_commit"
```

Use `.zip` for Windows and `.tar.gz` otherwise. Repeat identity checks for all six
targets. Authenticate each archive hash before extracting it. Record signed hashes,
unsigned reproducibility evidence, SBOM/security reports, notarization acceptance
and the exact successful tag pipeline.

### Native signature checks

On macOS, independently verify all three extracted executables for each Darwin
architecture with the trusted script:

```sh
for tool in pptxgengo pptxdesign wmdsdocs; do
  bash scripts/release/verify-macos.sh "$extracted/bin/$tool"
done
```

It checks Developer ID `Ryne Scott (VZJU7JS89T)`, identifiers, hardened runtime,
secure timestamp and tamper rejection. The protected Mac CI verifier also queries
Apple's live `Accepted` status for the downloaded notary submission ID. For an
owned runner with its existing notary profile, repeat `xcrun notarytool info` using
that profile/keychain; never expose keychain passwords. Bare CLIs cannot be stapled.

On trusted Linux with `osslsigncode` and its system CA bundle, independently verify
both Windows architectures against the fingerprint-pinned Microsoft signing root:

```sh
windows_ca=/absolute/new/private/v4.3.0-windows-ca.pem
bash scripts/release/install-windows-ca.sh --bundle-out "$windows_ca"
for tool in pptxgengo pptxdesign wmdsdocs; do
  bash scripts/release/verify-windows.sh "$windows_extracted/bin/$tool.exe" "$windows_ca"
done
```

This checks the Ryne Scott publisher, certificate chain, Authenticode signature,
timestamp and tamper rejection. It does not qualify Windows execution or PowerPoint.

### Resource and installation checks

From the verified native archive, check `template-catalog-manifest.json` records
`skill_included: true`, `registered_graphics: true`, `editing_profile: native-v1`,
`media_policy: placeholders`, the exact release commit and tagged bundle. Check
all inventory hashes; confirm the SQLite source counts/catalog search, template
deck coverage and all specialized runbooks. Run an ordinary `library-find` after
relocating the extracted directory. Run the packaged skill installer's
`--agent both --dry-run` first; actual installation or project migration are
separate operator actions. Preserve the downloaded release evidence and final
verification report outside the source checkout.
