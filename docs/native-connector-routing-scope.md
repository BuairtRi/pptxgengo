# Native connector routing implementation evidence

Operator instructions live in [architecture and geometry](../skills/west-monroe-presentations/references/architecture-geometry.md).
This ledger describes the v4.3.0 implementation and its named evidence.

## Representation contract

- One source relationship retains its authored ID and endpoint node/site pairs.
- Alternating orthogonal 3–6 vertex routes lower to `bentConnector2` through `bentConnector5`, with literal adjustment guides and endpoint flips/90-degree orientation. Adjustment precision is 1/100000 of the endpoint extent; no clipping of outlying guides occurs.
- Longer, diagonal, or zero endpoint extent detours retain their vertices as straight attached native segments and transparent one-EMU waypoint rectangles. Both neighboring segments attach to the exact top-center port of the same guide. Segments and guides occupy a closed ordered `.segment-NNN` / `.waypoint-NNN` namespace. Start/end arrows belong only to the logical ends.
- Every part retains renderer source ownership. Diagram inspection aggregates actual transformed segment points and lists the native parts. Logical containment measures the entire complete route allocation; missing/unknown parts are rejected.
- Receipt review and explicit geometry adoption preserve changed parts in YAML native overrides. Inspection and rebuild honor those overrides. Source composition/rerouting requires an explicit reviewed layout reset first; native movement does not mutate endpoint semantics or source waypoints.
- Custom connector geometry, unknown presets, formula guides and changed attachments remain manual review. No `p:cxnSp/a:custGeom` is generated by the routing planner or native override writer.

## PowerPoint compatibility finding

The parent qualification observed PowerPoint repair/removal for a generated custom-geometry connector deck. Removing those connectors opened cleanly; changing the custom geometry's text rectangle and fill did not resolve repair. This establishes a failure for those artifacts and that PowerPoint installation, rather than proving all custom DrawingML connector geometry is invalid. The replacement uses native presets or straight native connectors with attachment guides.

Microsoft documents [native connector types](https://learn.microsoft.com/en-us/office/vba/api/office.msoconnectortype) and [endpoint attachment behavior](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.connectorformat). The [Open XML connection-shape contract](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.connectionshape?view=openxml-3.0.1) leaves routing behavior to applications; valid XML alone does not qualify desktop behavior.

The named private macOS specimen is `native-multipart-routing/baseline.pptx`, exported from the V5 architecture derivative. It contains a same-axis U detour and a ten-vertex route around a service blocker. The parent observed a clean GUI open without repair and saved an edited copy; actual edit/reconciliation qualification is recorded by the parent. Windows desktop qualification remains outside v4.3.0 scope.
