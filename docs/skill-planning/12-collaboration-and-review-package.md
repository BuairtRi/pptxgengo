# Collaboration and independent-review package

**Proposed skill resources — October 2, 2026.** Companion to [the integrated operating model](11-integrated-presentation-skill-operating-model.md). These templates illustrate how the skill can preserve working context while giving an independent reviewer only the material its role requires. They are not installed skill files.

## Running project template

Create the project file at intake and expand it as work advances. Do not populate later stages with generic filler. Each substantive field should have a status such as confirmed, working, inferred, or open.

```text
Project / deck name:
Current stage:
Next useful move:
Operator's initial instructions and constraints:

Opportunity
  Client's stated need or ambition:
  Operator's understanding:
  Working interpretation and proposed response:
  Trigger / timing:
  Source IDs and unresolved conflicts:

Deck frame
  Core argument and current support:
  Reading mode: presented / emailed / hybrid
  Communication job:
  Intended reader outcome or next step:
  Priority audience and material secondary readers:
  Necessary detail / expected evidence:
  Main-deck length and expected reading time:
  Appendix policy / required RFP coverage:
  Frame version and operator feedback:

Value and differentiation
  Outcome, metric, baseline/target status, validation needs:
  Internal win logic:
  Client-facing reason to choose WM and supporting proof:
  Unresolved value or proof questions:
  Links to any seller-skill work:

Production state
  Narrative / outline version:
  Operator approval: version, date, decision, limits
  Slide-content version and review status:
  Composition plan and material fit choices:
  Deck path / version and QA status:
  Agreed independent review stages and audience lenses:

Links
  Annotated source index:
  Claim ledger:
  Audience context:
  Outline, slide content, internal page briefs:
  Composition plan, deck, review log:

Decision log / open questions
  Date; question or decision; status; evidence or reason;
  owner/input needed; affected page IDs; revisit trigger:
```

The decision log may contain the author's rationale. It is not part of the audience reviewer packet.

## Source-index entry

Use a stable ID and an accessible path or URL. Preserve the original source location when indexing a generated extraction or summary.

```text
Source ID / title:
Path or URL:
Type and origin: RFP / transcript / research / prior deck / seller output / ...
Author or meeting participants; date; version:
What it contains:
Why it matters to this opportunity/deck:
Useful pages, timestamps, headings, or slide numbers:
Claims or planned pages supported:
Authority, limitations, or conflicts:
Internal/client-facing use considerations:
Underlying source, if this is a summary or extraction:
Last checked; changed/missing/superseded status:
```

## Audience context template

This file describes the reader's starting position. It should not explain how the author arrived at the frame or coach the reviewer toward the intended conclusion.

```text
Audience context version:
Reading situation: email / presentation / hybrid; likely reading time
Primary audience: role, seniority, responsibility, decision rights
Other material readers: roles and influence
Relevant expertise: business, technical, industry; vocabulary familiarity
What readers already know: specific prior knowledge and its basis
What we cannot assume they know: our research, methods, acronyms, etc.
What they care about: outcomes, constraints, risks, questions
Evidence they are likely to expect:
Likely concerns or objections grounded in what we know:
Confidence and open questions: confirmed vs inferred audience assumptions
What the recipient would legitimately know about why they received this deck:
```

Do not add internal win strategy, working-session history, source findings the deck fails to disclose, or a statement of the answer the reviewer should reconstruct. If uncertainty about the audience could change the findings, ask the reviewer to state which inference it used and what changes under another plausible audience assumption.

## Review outline and slide-content formats

The narrative review packet needs more than titles:

```text
Audience-facing narrative summary: short statement of the proposed case
Main-flow length / intended reading time:
For each page in order:
  Stable page ID and proposed title
  Intended point or precise subject
  Planned visible support or explanation
  Connection to the preceding/following page
Appendix entries: role and main-flow reference, when relevant
```

After outline approval, the content reviewer sees the exact planned visible content:

```text
Page ID and title:
Planned on-slide copy:
Planned chart/table/diagram: values, labels, relationships, explanatory copy
Visible source line / material qualifications:
```

The author retains page jobs, private rationale, source analysis, and gaps in separate internal briefs. Reviewer packets must not fill missing on-slide explanation with those notes.

## Independent reviewer prompts

Start each review in a fresh context and supply only the listed packet. Do not fork the creator's full history. Use a new packet/version for a material revision so findings remain traceable. If only author self-review is available, record that limitation rather than calling it independent.

### Narrative and outline review

**Inputs:** audience context, audience-facing narrative summary, and review outline.

```text
Review this planned presentation from the supplied audience's starting
knowledge and priorities. You have not participated in its development.
Use only the supplied packet; do not assume facts or explanations from
other conversations.

First explain, in your own words, the main argument, its supporting logic,
and the requested understanding or next step. Identify where the sequence
does or does not make sense for these readers.

Find missing premises, unsupported jumps, vague claims, audience mismatches,
repeated pages, unnecessary detail, and evidence that the plan would need.
Assess whether the main flow is appropriately tight for the reading budget.
Distinguish an outline gap from something that can reasonably be resolved
when individual slide copy is written. Do not assess final visual design
or claim to verify source accuracy.

For each material finding, cite page IDs and the relevant wording, describe
what a reader might conclude or fail to understand, explain why it matters,
and suggest a bounded repair. State uncertain audience assumptions.
```

### Slide-content clarity review

**Inputs:** audience context and ordered reader-facing slide-content drafts.

```text
Read these slide drafts as a recipient with the supplied audience context.
Use only content planned to appear on the slides. Do not invent a talk track
or an author explanation to bridge a gap.

Explain the overall point and next step. For each problematic slide, say
what you think it means, where you had to guess, and which missing term,
premise, mechanism, evidence explanation, or qualification caused that guess.
Check that the planned visual's labels and relationships make sense.
Identify excessive detail, repetition, unexplained jargon, and promotional
language that weakens the argument. Check transitions between slides.

For each finding, cite page IDs and wording, describe the reader impact,
and propose the smallest useful repair. Treat planned visuals as content
specifications; final visual fit and legibility have not been tested yet.
```

### Finished-deck audience review

**Inputs:** audience context and rendered slides in order. Supply a talk track only if the explicitly agreed test is the combined presented experience.

```text
Review this deck as the supplied audience would encounter it. Explain the
central argument, why it matters to you, and what it asks you to understand,
consider, decide, or do. Do not use hidden author notes to explain an emailed
deck.

Identify unclear content, weak evidence as presented, missing explanations,
confusing visuals, abrupt transitions, excessive reading effort, and questions
that prevent you from responding. Be specific about what you see on each
page and what you cannot infer. Assess relevance to your role and priorities.

Report material issues with page IDs, observed content, reader interpretation,
and a practical repair. Distinguish comprehension issues from personal
preferences and from matters that require underlying source verification.
```

## Author response and revision record

Review is complete when the author has assessed the findings and the necessary revisions have been made or brought to the operator. A score or an unaddressed reviewer report is not sufficient.

| Field | What to record |
| --- | --- |
| Stage and version | Packet reviewed, audience lens, review scope, and page IDs |
| Finding | Observed wording or visual and the reader's interpretation |
| Author assessment | Accept, partly accept, decline with reason, or ask operator |
| Proposed change | Specific narrative, copy, evidence, or design repair |
| Operator input | Material decision, feedback, or approval when required |
| Resolution | Changed artifact/version, unresolved issue, and affected recheck |

Keep the initial reviewer uninformed by the creator's rationale. If discussing its findings afterward, preserve the original report and label the exchange as a follow-up. Recheck affected content after a material change; return to outline approval if the narrative itself changes.
