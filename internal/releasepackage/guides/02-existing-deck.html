The editable source is YAML. A generated PowerPoint is an output, not a live connection to the project. Source builds after v4.1.0 provide reviewed proposals for uniquely mapped plain text via project reconcile propose and explicit adoption via project reconcile adopt. Read the packaged docs/text-reconciliation.md before using them. Stable v4.1.0 predates these commands. Rich text, geometry, structure and ambiguous objects still require manual review; Mac and Windows desktop identity survival remain unqualified.

A. Resume an editable YAML project

  1. Make a working copy of the whole folder. Retain the original, including builds/, state.json, locks, assets and decision history. The examples below assume your copy is at C:\Work\Client deck.
  2. Read the project context file referenced by deck.yaml (often project.md or context/project.md) and the composition log. Ask the CLI for slide IDs and the current review state:
pptxgengo design project status --project 'C:\Work\Client deck'
pptxgengo design project titles --project 'C:\Work\Client deck'

If this project came from a Mac or an older release: inspect the upgrade before changing its lock. Migration validates compatibility and fit; it does not rewrite the copy or redesign local templates.

pptxgengo design project migrate --project 'C:\Work\Client deck' --dry-run

Read the result. If you intend to move the working copy to this installed release and the dry run succeeds, run:

pptxgengo design project migrate --project 'C:\Work\Client deck'
pptxgengo design project check --project 'C:\Work\Client deck'

The old lock is preserved. Report compatibility errors to your agent; do not delete the lock to bypass them. Rebuild and review after migration because prior approvals and native review coverage become stale.

My deck.yaml is one enormous file

Ask your agent to split the project using the bundle matching its lock. After migration to V11, this command moves slides, notes and local templates into separate files:

pptxgengo design project split --project 'C:\Work\Client deck' --bundle v11

Splitting reorganizes the source without intentionally changing the deck. Do it once, early, then work on individual slide files.

The generated PowerPoint was edited by hand

Keep that edited PowerPoint separately. Ask the agent to inventory it, identify the operator's changes and port the intended changes into the YAML. A changed build baseline can block build and export. Do not overwrite it or pretend its edits are already in the source.

B. Open a maintainer ZIP

  1. In File Explorer, right-click the ZIP and choose Extract All. Use a new folder you can write to.
  2. Find deck.yaml inside the extracted contents. Its containing folder is the project path for CLI commands; do not point the CLI at the ZIP itself.
  3. Keep all extracted source, evidence, assets, history and builds together. Follow entry point A, including the migration dry run for a Mac handoff.

A client ZIP contains the delivered PowerPoint, not editable YAML. If there is no deck.yaml, request a maintainer export from the author or use the PowerPoint-only path below.

Internal material: maintainer packages include private project context and evidence. Share them with the next author, not the client.

Where do I edit the words?

In a split project, open slides/<slide-id>.yaml. The content section holds readable copy such as headlines, card titles and body text. bindings connects those fields to template slots. Some slides instead use values in the template's own shape.

id: situation
template:
  scope: shared
  id: cards/3
content_kind: supplied_content
notes_file: notes/situation.md
content:
  eyebrow: What we heard
  headline: Three changes can reduce delivery friction
  # The complete slide file also contains its cards and bindings.

This is a location example, not a complete buildable slide. Keep the existing required fields, bindings and fixed item counts. Ask the agent to scaffold a complete slide when adding one.

File or folderWhat it controlsWhen you touch it
deck.yamlDeck order, sections, asset and context links, local template references.Reordering, adding slides or changing deck metadata.
slides/Each slide's copy, template selection, image references and slide settings.Most everyday revisions.
notes/Speaker notes linked by notes_file.Presenter guidance. These are separate from visible body copy.
templates/Project-local layout definitions.Intentional custom design. A change affects every slide using that definition.
composition-log.yamlEach slide's purpose, selected template and mapping rationale.Update alongside slide additions, removals and layout changes; retain meaningful prior decisions.
builds/Generated PowerPoint, layout report, object map and receipts for each build.Read and review. Keep history; do not use outputs as the editable source.

Stock versus local: scope: shared selects a library template without copying its design into your slide. scope: local selects a project definition, often a deliberate derivative. A name such as “semantic-001” alone does not tell you how customized a slide is; inspect its scope and composition log.

Windows paths: quote filesystem paths in PowerShell. Inside YAML, keep project-relative references with forward slashes, such as notes/situation.md; no absolute paths or ...

More text without redesigning the layout

The slide can use Comfortable, Compact or Dense body typography. The header stays Comfortable unless explicitly changed. Automatic fitting can step the whole body down and report a warning; it does not enlarge geometry or change fixed item counts. Put these settings beside template, outside content:

density: compact
header_density: comfortable
auto_density: false

Template limits still apply. Review small text at presentation size; a successful build does not establish readability.

C. Rebuild from a PowerPoint-only source

Preserve the original. The inventory command extracts slide text, positions, tables, charts, images and notes into reports; it does not convert PowerPoint into an editable YAML project or map slides automatically.

pptxgengo design source-inventory --in 'C:\Work\Original deck.pptx' --out 'C:\Work\Original inventory-1'

Use a new output folder. Read source_inventory.md with the agent and visually inspect the original in PowerPoint. Text extraction cannot replace understanding the diagram or the argument.

  1. State each slide's job. Is it a comparison, roadmap, interview list, heat map, commercial proposal or another relationship?
  2. Search the stock library by purpose and structure. Inspect candidate screenshots and authoring slots before selecting one.
  3. Fit the content deliberately. Retain related story units, rewrite only as agreed and record every mapping against the original slide number. Avoid splitting solely because an easy layout has little room.
  4. Build a new project and PowerPoint. Start from the bundled project example; replace its synthetic content. project init pins an existing project—it does not create all source files or convert a PPTX.
  5. Review the original and rebuilt deck side by side. Account for content and meaning, not merely the slide count.

Find a template, then inspect its copy fields

pptxgengo design library-find --query 'phase roadmap' --kinds template --limit 10 --summary
pptxgengo design library-find --structures sequence --items 4 --kinds template --summary
pptxgengo design library-preview --id lifecycle/three-phases
pptxgengo design library-authoring --template lifecycle/three-phases

The discovery output supplies verified screenshot paths. Open those images; library-preview reports preview information, not a new custom render. Authoring information explains aliases, required fields and approximate capacities. Choose keys from actual search results rather than inventing them.

Agent setup: copy the packaged starter

This PowerShell example creates a new project directory from the bundled example. Choose a path that does not already exist:

$paths = pptxgengo paths | ConvertFrom-Json
Copy-Item -LiteralPath $paths.project_example -Destination 'C:\Work\Rebuilt deck' -Recurse
pptxgengo design project init --project 'C:\Work\Rebuilt deck'
pptxgengo design project split --project 'C:\Work\Rebuilt deck' --bundle v11

The copied example is not your deck. The agent must replace its slides, context, template and assets with your content, update the composition log and validate the complete result.

Build, inspect, then deliver

1. Make the source edit and update the slide's composition-log entry to reflect the revision. Validate and build:

pptxgengo design project check --project 'C:\Work\Client deck'
pptxgengo design project build --project 'C:\Work\Client deck'

Each build creates a new builds/<build-id>/ directory. Use the path printed by that command. Replace BUILD-ID below with that actual folder name; do not type the placeholder literally.

2. Read density warnings and measure the report. Measurement takes a report path, not --project:

pptxgengo design project measure --report 'C:\Work\Client deck\builds\BUILD-ID\layout-report.json'

3. Review the generated PowerPoint. Windows native export is experimental and awaiting a real Windows smoke test. It needs desktop PowerPoint in your signed-in session and the installed IBM Plex fonts.

pptxgengo design render-doctor --json --timeout 60s
pptxgengo design render --pptx 'C:\Work\Client deck\builds\BUILD-ID\deck.pptx' --out 'C:\Work\Client review-1' --pdf --png --contact-sheet

Use a fresh review directory. Inspect full-size slide images for clipping, wrapping, spacing, font substitution and content loss. A contact sheet helps compare the deck but is too small for detailed text checks.

Native export failed—how do I continue?

Read render-error.txt in the output folder and look at the PowerPoint window for a reported setup, activation, Protected View or policy issue. Resolve the actual issue, then retry once into a fresh folder. Do not change global security policy or retry repeatedly.

As a fallback, open the new build in PowerPoint and export a PDF or slide images manually for visual review. Keep the generated PPTX unchanged. Manual export does not create the signed CLI receipt required by project attach-render; record that native CLI coverage remains pending.

After successful CLI rendering, attach its signed evidence to the current build. This records render coverage; actual visual approval needs real review decisions.

pptxgengo design project attach-render --project 'C:\Work\Client deck' --render 'C:\Work\Client review-1'

4. Export to a new ZIP path:

pptxgengo design project export --project 'C:\Work\Client deck' --mode client --out 'C:\Work\Client delivery-1.zip'
pptxgengo design project export --project 'C:\Work\Client deck' --mode maintainer --out 'C:\Work\Author handoff-1.zip'
  • Client: current PowerPoint and export manifest; no editable source or internal project material.
  • Maintainer: source, context, evidence, assets, decisions, approval history and current build for the next author. Treat it as private.

Exports require a current build and an unchanged build baseline. They create local archives, not emails or uploads. A PDF is a separate render output.
