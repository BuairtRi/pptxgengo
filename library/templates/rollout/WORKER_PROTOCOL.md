# Template rollout implementation protocol

All 65 shortlist items are assigned now. Each worker owns its lane directory only.
No five-template scheduling gate applies. Native PowerPoint work belongs to root.
The earlier WM slide skill is a legacy asset, not the implementation authority.

## Per-template output

Under the assigned `implementation_directory`, write:

1. `contract.json`: executable `pptxgengo.component-contract.v1` for existing
   `pptxcomponent inspect|apply`. Pin source and scene hashes. Expose meaningful,
   stable semantic slots covering useful title/body/labels. Group rich-text runs
   logically, retaining exact binding cardinality. Exclude legal/footer/page number.
2. `example-values.json`: accepted `slots` arrays and optional `profile`; materially
   change substantive body content as well as headings. Keep realistic density
   without silent shortening or artificial source-length capacity claims. Use an
   explicitly illustrative modernization-planning scenario; do not invent client
   results, testimonials, commitments, or named staff. Mark unavoidable residual
   source facts/artwork in metadata. Do not represent source-reference decks as
   clean client deliverables.
3. `implementation.json`: schema `pptxgengo.template-implementation.v1`, template_id,
   family_id, source, source_sha256, scene_sha256, preview (path/hash), lane,
   category, altitude, density, role, takeaway, components (reusable groups with
   object_ids and semantic purpose), slot_notes, style_notes, opaque_areas,
   retained_source_content, limitations, status. Status initially `implemented`;
   native rendering/fit/visual qualification are separate root-managed gates.
   Include `adaptation_mode: fixed_source_geometry`, `native_fit: not_measured`,
   `adaptation_qualified: false` and accurate flags about change coverage.

## Required process

- Inspect the exact source PNG for each template. Reuse extracted scenes prepared
  by root at the paths in `assignments.json`. Do not mutate source scenes.
- Read scene bindings and object relationships before assigning slots or styles.
- Preserve source typography/geometry/assets. Fixed cardinality is a supported
  boundary, not proof of dynamic reflow. Do not use source character count as a
  measured capacity limit.
- Add semantic color roles only for individually inspected explicit RGB binding
  paths. Source and at least one alternate profile are useful where safe; retain
  data/actor/phase/status colors and all logos. Existing contract roles currently
  accept `fill.srgbClr.val` only (including explicit text color fills). Theme colors
  and opaque images remain unsupported. Never globally replace matching hex codes.
- Per role, include only bindings with the same verified source color, so `source`
  restores the exact reference. No full inverse profile without foreground/surface
  evidence. A bounded title or rule emphasis profile is acceptable if disclosed.
- Preserve diagrams/charts/images and report exactly which remain opaque. Chart
  data and image content are not editable text merely because labels are editable.
- Run actual `pptxcomponent inspect` for each contract and fix invalid bindings.
  Root will run application/build/render operations. Do not run or add test suites.
- Review worker outputs for complete ownership and no copy-derived slot names.
- Keep code helpers inside your lane; do not edit shared Go/Python files, source
  review records, shortlist, assignment manifest or another lane's files.
- Do not invoke PowerPoint, rebuild frozen native binaries, or claim native QA.
- Send progress as items finish; continue through your whole assigned backlog.
