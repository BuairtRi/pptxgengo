# Capability review deck

## Proposal complexity benchmark

The user reviewed `showcase-v1` and found it too simple for detailed proposals.
It remains a mechanics baseline. The current benchmark is the five-slide
[dense proposal spec](dense-deck.json), generated by
[build-dense-showcase-spec.py](../../scripts/build-dense-showcase-spec.py):

| New slide | Reference pattern | Required complexity |
|---|---|---|
| Five-phase approach | EnableComp 3 | Five phase columns, activities, evidence/output lane, timing |
| Phase detail | UHG 28 | Objective/exit sidebar, four paired activity/work-product rows, acceptance and scope panels |
| Workflow matrix | EnableComp 4 | Five workflows aligned across constraints, operating model and measures |
| Delivery organization | UHG 43 | 21 roles, three pods, shared specialists, client counterparts and leadership narrative |
| Release roadmap | UHG 38 | Twelve months, seven overlapping workstreams, accountable owners and decision evidence |

These are new editable compositions with synthetic content. They are not exact
reconstructions of the references. Source deliverable montages, shaped ribbons,
hatched extensions, rich-text emphasis and arbitrary nested group semantics
remain separate fidelity requirements. Word/object counts help detect sparse
examples; they do not establish visual quality or interchangeable templates.

Use explicit padding once: either a text frame covering its surface with native
insets, or a smaller frame inside that surface with zero insets. The dense generator
uses the former for matrix cells and the latter for panels and bullet lists.
Native fit, final verification and inspection of every rendered slide are required.
The accepted fixture is recorded in [dense-proof.json](dense-proof.json), including
the native measurement results, visual review, exact artifact hashes, source-density
comparisons and recovery limitations. Temporary PPTX/PDF/PNG files remain local.

Both decks use a synthetic software modernization proposal to exercise the authoring
system. Neither presents actual client findings, delivery commitments or benefits.
The [story](story.md) records the initial narrative brief; the [executable spec](deck.json)
is the final authored copy and geometry. Slides each carry a role and takeaway.

## Rebuild

For the dense benchmark, use `scripts/build-dense-showcase-spec.py` and
`library/showcase/dense-deck.json` in the same probe/measure/build/verify sequence.
`fit-report` uses the same spec, bundle and evidence arguments as `build`, and
reports every fixed text-zone failure alongside the full planner result. After
rendering, inspect all five slides. The local `scripts/report-dense-showcase.py`
records the accepted fixture and regenerates its recipe records from exact hashes.


From repo root, first hydrate the files named in `assets.json` to `samples/showcase/assets/`.
Keep original and derived-file hashes intact. The helper below regenerates the spec;
it does not download or alter assets.

```sh
python3 scripts/build-showcase-spec.py
go build -o /tmp/pptxcompose ./cmd/pptxcompose
/tmp/pptxcompose probe --spec library/showcase/deck.json --out samples/showcase/probes
/tmp/pptxcompose measure --bundle samples/showcase/probes --out samples/showcase/evidence.json
/tmp/pptxcompose build --spec library/showcase/deck.json --bundle samples/showcase/probes --evidence samples/showcase/evidence.json --out samples/showcase/deck
/tmp/pptxcompose verify --bundle samples/showcase/deck --out samples/showcase/verification.json
```

Every output path must be new. Native measurement/export requires macOS PowerPoint.
Never run parallel PowerPoint automation against the same instance. Measurement
leaves its generated deck open. Close only task-owned unedited presentations before
repeating a command with the same filename. Export and inspect every slide using
`scripts/export-powerpoint.applescript` and `scripts/render-pdf.swift`.

## Scope of the review

The sample demonstrates reproducible new composition, bounded text-fit contracts,
selected brand assets and native editability. Its shapes and comparison table are
editable objects; they are not native chart/table data models. Arrow positions are
authored, not inferred from narrative meaning. Layout fields remain explicit;
there is no automatic general-purpose visual designer.

For decks generated by this CLI, `recover-text --text-only` can return text edits
to the original spec when object names/order/frames and images remain unchanged.
It restores original styling and does not import colleague formatting or notes.
Source-scene extraction preserves more general returned PPTX files as editable JSON
bindings and raw OOXML resources. General semantic reconciliation and YAML import
remain unimplemented. Source-sized pod variants,
arbitrary typography inheritance, broad catalog promotion and general arrow routing
remain separate work.

## Retrieval

`recipes.jsonl` records the five native-verified dense slide
recipes with the exact spec/proof hashes. Append these records to the existing
catalog extras when rebuilding SQLite, then search `--kind dynamic_recipe`.
Recipes have `native_fixture_verified` status and `adaptation_approved: false`.
They are measured examples with explicit geometry, not inferred general layouts.
The eleven-slide v1 mechanics baseline is not promoted by this proof.
